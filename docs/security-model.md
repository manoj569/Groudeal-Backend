# Security model

Identity hashes passwords using the framework password hasher; minimum 12 characters, uppercase/lowercase/digit/symbol. Password maximum is 128. Five failed logins lock the account for 15 minutes. Email is unique after normalization. Unknown users receive the same login error and a dummy password verification. Email and phone verification remain false: no verification is implied by registration.

JWT uses HMAC-SHA256 with issuer, audience, lifetime, signing algorithm and signature checks. Startup requires an external signing key of at least 32 UTF-8 bytes. Default lifetime is 15 minutes, bounded 1–60 minutes with 15 seconds clock skew. Every authenticated request also checks account active status, database token version and current role memberships. Removing a claimed role invalidates old tokens; newly granted roles require login. Logout increments token version atomically and revokes all existing tokens. Refresh tokens are not implemented; log in after expiry. Database seller eligibility is checked after acquiring and refreshing locked seller state on every seller write and join.

Registration has no role/status/verification inputs; unknown fields are rejected. Every new account receives only Customer. Any authenticated customer can request a seller profile. An Admin explicitly approves seller details and grants Seller. Write authorization also checks seller owner ID, product ownership, pickup ownership and eligible verification status; role alone is insufficient. Profile changes reset review. Cross-owner writes return 404; public responses omit customer IDs/contact details and private seller verification fields.

Admin bootstrap is the restricted audited operator CLI plus supervised MFA enrollment described in admin-mfa-provisioning.md. Public registration grants Customer only; never grant Admin through ad hoc application HTTP/SQL. The command operates on an independently verified existing account, creates no credentials and uses separately controlled operator privileges. Explicit Development fixtures are synthetic only and also require MFA.

HTTPS redirection and HSTS apply outside Development. Configure an HTTPS endpoint/certificate and explicit AllowedHosts in hosting. CORS defaults to no permitted origins and rejects wildcard origins. Add only trusted origins via `Cors__Origins__0`. No credentialed cross-origin cookies are used. IP-based rate limits: global 300/minute; auth group 10/minute. Do not trust unvalidated forwarded headers; configure known proxy handling before deployment behind a reverse proxy. Single-process rate limits are appropriate for this single-instance MVP; they are not distributed limits.

Kestrel body size is 64 KiB; pagination caps at 100. JSON rejects extra fields. FluentValidation constrains inputs, enum values, precision, slugs, contact fields, attributes and lengths. EF parameterizes queries; row-lock SQL uses interpolated parameters. CORS and security headers include nosniff, no-referrer, restrictive CSP and no-store. Errors use Problem Details and avoid SQL details. Audit writes share the business transaction. No password, JWT, body, OTP, payment credential or document payload is logged. Error logging records exception type/trace rather than potentially sensitive exception strings. Keep EF sensitive-data logging disabled.

Reservations are non-financial; there are no payment tokens, payment statuses or refunds. Audit storage contains actor/entity identifiers, fixed action names and bounded review-reason metadata; operators must exclude secrets and unnecessary personal data. Database credentials, signing keys and demo passwords come from environment variables; no production secret is committed.

## Sprint 2 operational safeguards

### Sprint 2.1 owner reads and product status

GET /seller/profile requires an active authenticated account and scopes exclusively to JWT actor ownership. It intentionally does not require Seller because Pending/Rejected onboarding accounts may have Customer only. Contact/FSSAI/coordinate/review-time fields are returned through a dedicated private DTO, never added to public seller responses. The existing no-store headers and token-version/current-role validation apply. No arbitrary seller ID, reviewer identity or invented review notes are exposed.

GET /seller/products and PUT /seller/products/{id}/status require Seller; writes additionally lock and reload current seller approval state and constrain the product query to that seller. Only the existing Active/Inactive enum is accepted; unknown/missing/null status is rejected, unchanged status is a safe no-op, and changed states are audited. Deactivation cannot bypass a live campaign, legacy live row, outstanding stock hold, Active reservation or Pending/Ready pickup. Activation checks category/variant eligibility. Status changes share the exclusive seller lock with allocating/fulfilling campaigns, preserving inventory commitments during concurrent submission. No status field was added to the existing full product-update input, so it cannot bypass the guarded status route.

GET /seller/pickups/{id} requires Seller and filters the pickup through its seller's current owner ID. Missing and cross-owner IDs both return 404; there is no Admin ownership override. It uses the same explicit PickupDetailResponse projection as operational lists, with no customer contact/account ID, code/hash/expiry, attempt/lockout or collector fields. Reads do not generate pickup secrets or allow self-collection. Seller ownership remains required even if the caller is also a Customer.

The seller frontend stores these private query results only in its existing user-scoped in-memory cache, clears them on authentication removal, and never persists profile data or code secrets. It now reads direct owner APIs rather than paging through pickup lists or using the public catalog as an ownership source. Public endpoint shapes and service-worker API-cache exclusions remain unchanged. PostgreSQL tests verify owner/onboarding access, cross-owner denial, precise pickup-field allowlists and status/submission race outcomes.

Seller inventory, campaign lists/reservations/performance and pickup endpoints require Seller and owner scoping. Customers cannot view another customer's reservation, pickup, code or notifications; customer roles cannot invoke seller collection. Code issuance and collection both lock seller, campaign and pickup consistently. Seller approval and active-owner status are rechecked for operational pickup writes. Publication and reservations also recheck active product/category/variant and pickup eligibility.

Pickup eligibility is explicit: confirmed inventory-backed campaign, ReadyForPickup record, active reservation, unexpired pickup window, unlocked attempts, unexpired matching code and authorized seller. PaymentPolicy is NotTrackedOfflineResponsibility; the system neither requires nor asserts a paid status. Seller readiness and physical collection are operational evidence only. Any legal/commercial offline payment handling remains the seller's separate responsibility and must be agreed before a live pilot.

Pickup codes contain 128 random bits (32 uppercase hexadecimal characters), generated by RandomNumberGenerator. Only SHA-256 of pickup-ID + code is stored, compared in constant time. High entropy prevents practical offline enumeration of a database hash; these are not six-digit PINs. The owning customer requests a code via POST only after Ready; plaintext is returned only in that response with no-store headers. Codes expire after 30 minutes or pickup deadline, whichever comes first. Reissue is allowed after one minute, invalidates the previous hash and does not clear failed-attempt lockout. Lost responses can therefore recover without storing plaintext. Frontends must not put codes in URLs, logs, analytics, persistent shared storage or seller listing DTOs.

Collection atomically clears the hash and records collector/time, completes that reservation, consumes stock, saves audit/notifications and checks group completion. Replay/parallel collection cannot consume stock twice. Incorrect or expired well-formed codes persist a failed attempt even though the response is 400; each five failures locks the pickup for 15 minutes. Malformed codes are rejected before database verification. Endpoint throttling adds 30 code operations/minute/authenticated actor, in addition to global IP throttling; attempt lockouts persist across instances/restarts. Single-instance HTTP rate counters still require shared infrastructure before horizontal scaling.

Confirmation/rejection requires a bounded ASCII idempotency key. Same key/outcome/reason returns current campaign state without new pickups/notifications; changed payload or a second key conflicts. Deadline checks occur under lock, so a delayed worker does not permit late confirmation. Customer cancellation closes as soon as the target fills. Legacy transition routes cannot skip confirmation or successfully complete unverified pickups.

Notification records are committed with business state and have unique delivery keys. GETs and read acknowledgments scope by recipient; no pickup secrets or unnecessary customer PII appear in seller reservation DTOs. Worker failures log safe campaign ID/error type, roll back the candidate transaction, persist bounded retries and continue. Admin-only health exposes backlog, retries, legacy cutover needs and worker heartbeat. Raw exception messages, code bodies and secrets are excluded from application error logs. Validate this policy at the production reverse proxy and log sinks as well.

Required regex fields now reject null explicitly (postalCode, contactPhone, slug and idempotencyKey). Inventory and pickup DTOs validate decimal precision, discrete units, version and code shape. Sprint 1 role-revocation and stale-approval regression tests remain in the suite.

Remaining production acceptance work: actual target runtime/image patching, identity ownership/password recovery and anti-bot/support controls, real operator IAM/MFA recovery drills, formal FSSAI/other seller review, approved audit/PII retention/archive policy, target database least-privilege/TLS and backups/restore/PITR, key rotation, external monitoring and proxy/rate-limit verification. Sprint 5 code closes the runtime/MFA/provisioning implementation gaps; local tests do not certify target infrastructure.

## Frontend Sprint 3 administration

The /admin workspace requires an authenticated Admin account and a successful protected health probe before showing operational content. Client role checks are convenience only. Every new API belongs to RequireAuthorization("Admin") and checks Actor.IsAdmin again in its application service. Existing current-role/token-version/account validation remains. No public Admin registration, role management, arbitrary mutation or seller-ownership bypass was added. Admin provisioning remains the controlled operator procedure above; MFA is still a production gate.

Private admin queries use the existing private/admin/userId cache namespace; auth expiry, API 401 and logout remove private queries and mutation history. Tokens and admin data are not persisted to browser storage or service-worker API caches. API 403 hides the workspace or affected view, including cached data; it never falls back to unrestricted public lookups. User strings are rendered as React text, not HTML. Desktop tables and mobile cards share the same server-paginated data.

Seller contact/FSSAI/location details are restricted to the approved owner/private or Admin review contracts. Governance reservations/pickups omit customer account/contact data. Neither Admin DTOs nor audit rows return pickup code/hash/expiry/lockout fields, password/security-stamp/Identity data, raw log payloads or stack traces. Retry error text is normalized. Audit JSON is projected through an action/key/type/length allowlist; the frontend also ignores unknown metadata keys. Audit actor references/display names are restricted operational identifiers. Direct operator writes remain a trust boundary; do not place secrets in free-text review reasons, names, correlations or other business fields.

Administrative approval/rejection requires an explicit review dialog and in-flight submit lock. Rejection reason is mandatory on the backend and UI, bounded to 500, and saved in the existing audit transaction. Approval reasons remain optional. Existing state/eligibility checks are authoritative under seller/campaign locks. Already-reviewed records conflict, avoiding duplicate mutation audit; there is no automatic HTTP mutation retry. After transport/5xx/409 uncertainty the dialog blocks repeats and instructs a close/refresh before another action, because review endpoints have no idempotency-key contract. No force-complete, force-retry, raw record editor or financial action exists.

Server-side pagination and bounded search/status/date/ID filters reduce unnecessary data retrieval. Existing indexes support status/time/history scans, but substring search/aggregate counts need profiling before large-scale rollout. Counts are operational READ COMMITTED snapshots, not certified reports. Monitoring displays persisted failures, deadlines and a process-local heartbeat; it neither guarantees external process liveness nor replaces alerts. Sprint 5 adds Admin MFA and runtime audit tamper protections; external retention/archive approval, operator verification standards and target production deployment evidence remain required.

## Sprint 5 authoritative security changes

.NET 10 LTS and the supported package baseline supersede the Sprint 4 runtime gap; see sprint5-verification.md for executed evidence. Every Admin must complete MFA in every environment. Password verification returns an opaque short-lived challenge, not a usable Admin/Customer JWT. Identity TOTP plus persistent replay protection and encrypted single-use recovery codes are implemented; Admin policies require MFA and authentication rechecks current enabled factor/roles/status/version. Customer/Seller behavior and ownership guards are retained.

The former manual Admin SQL bootstrap procedure is superseded by the explicit restricted operator CLI in [admin-mfa-provisioning.md](admin-mfa-provisioning.md). It operates on an independently verified existing active account, never creates passwords or real accounts automatically, writes transactional security audit and invalidates sessions. Revocation also works for suspended accounts without reactivation. Approved MFA reset clears factor lockout, rotates secrets, invalidates codes/sessions and opens supervised re-enrollment; it does not reactivate a suspended profile or provide password recovery. Runtime privilege templates deny Admin membership changes and MFA reset/enrollment authorization. Privileged operator IAM and ticket verification remain external trust boundaries.

Production fails closed without persistent certificate-encrypted Data Protection keys, verified-TLS PostgreSQL, bounded pools/timeouts, explicit allowed hosts and no Development fixture configuration. Forwarding accepts only configured proxy IPs, one symmetric hop. Structured diagnostics use safe error type/trace; raw framework EF/JWT exception streams are suppressed. Server error detail and EF sensitive logging remain disabled. API and token responses are no-store; factors/challenges are POST-body values. The frontend holds factors only transiently, requires acknowledgment of one-time recovery codes and binds unauthorized callbacks to the token that actually sent a request, preventing a stale 401 from clearing a new session.

The additive MFA migration introduces purpose-bound challenges, accepted-code digests and a nullable enrollment window; it does not backfill accounts/campaigns or change business quantities/prices. Existing Admins lacking MFA are blocked until controlled enrollment. No plaintext legacy-token fallback exists. Audit/security history is retained; no automatic purge is implemented. Runtime cannot update/delete audits. A separately approved retention/archive policy remains a pilot gate.

The existing worker now exposes finite retry exhaustion and per-item progress and stops cleanly with host cancellation. Readiness/liveness probes and production templates exist, but Docker/target-host tests, actual TLS/DB grants, real key management, operator IAM, backups/PITR, legal seller review and legacy reconciliation remain external acceptance requirements. See [operations runbook](production-operations-runbook.md) and [readiness statuses](production-readiness-checklist.md).
