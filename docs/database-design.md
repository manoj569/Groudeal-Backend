# Database design

EF migrations are the schema source of truth; startup never calls EnsureCreated or automatically migrates. `schema.sql` is generated from the checked-in migration for review.

| Table | Relationships and purpose |
| --- | --- |
| identity_accounts | Identity credentials; UUID key, normalized unique email, lockout, token version |
| identity_roles, identity_user_roles | Customer, Seller, Admin assignments |
| identity_user_claims, identity_role_claims, identity_user_logins, identity_user_tokens | Standard Identity foundation |
| users | Domain profile, 1:1 Identity account; nullable unique email/phone, account status |
| sellers | One profile per owner; reviewer references users |
| seller_locations | Many locations per seller; active pickup flags and optional coordinates |
| categories | Self-referencing parent, unique slug; seeded grocery hierarchy and inactive future roots |
| products | Seller-owned, belongs to category; unique seller/slug |
| product_variants | Composite seller/product FK, unique seller/id and SKU, unit definition, constrained JSON attributes |
| group_buy_campaigns | Seller, variant, pickup location; composite seller/variant and seller/location FKs prevent cross-seller references |
| group_buy_reservations | Campaign/customer FKs, quantity, immutable price snapshots, lifecycle and idempotency key |
| audit_logs | Nullable actor FK, action, entity, UTC timestamp, safe JSON metadata |
| inventory | Unique variant FK, composite seller/variant FK, available quantity and explicit optimistic version |
| pickup_records | Unique reservation FK, composite seller/campaign FK, customer and collector FKs, status, approved instruction snapshot, deadline, code hash/expiry and persisted attempt lockout |
| internal_notifications | Recipient FK, notification type/entity, created/read times; globally unique recipient/type/entity deduplication key |

All business primary keys are UUIDs. Identity's standard claim IDs use integer keys. FK deletes are restricted; lifecycle states are used instead of blanket soft deletion. Tables use snake_case and columns use consistent quoted PascalCase generated by EF. Domain timestamps map to timestamptz. Npgsql maps campaign RowVersion to PostgreSQL `xmin` (xid), not SQL Server rowversion.

Money uses numeric(18,2); quantities numeric(18,3); coordinates numeric(10,7). Reservation quantities count campaign variant units: a 5 kg pack has UnitQuantity=5, UnitOfMeasure=Kilogram, and a reservation of 2 means two such packs. Reference/group price are per variant unit; targets and reservation limits use that same unit. Piece/pack counts are integral. Total price is rounded away from zero to 2 decimals; the DB check uses PostgreSQL round with the same behavior for positive values.

Checks enforce positive prices, reference >= group price, valid capacity bounds, positive reservation quantity, valid reservation totals, min/max bounds and start < expiry. Unique (CampaignId, CustomerUserId, IdempotencyKey) defines retry scope. Keys remain reserved after cancellation/expiry. A retry with another quantity returns 409; same payload returns its existing record even if campaign is now closed. New keys express new commitments.

Reservation transaction at READ COMMITTED: acquire seller FOR UPDATE, campaign FOR UPDATE; recheck idempotency, seller/account eligibility, product/category/variant/pickup, declared stock backing, server time, limits and remaining capacity; insert price snapshot; increment reserved quantity. At full capacity, apply TargetReached and then AwaitingSellerConfirmation in the same transaction, persist the confirmation deadline and seller notifications, write audit and commit. Seller-wide exclusive locks also serialize inventory declarations, campaign submissions and collections. Workflows acquire seller before campaign before pickup, avoiding inverted lock order. The acquired seller/campaign is reloaded to avoid stale EF tracking values.

Cancellation locks campaign before loading the reservation, checks customer ownership and releases reserved capacity exactly once while Open and before acquisition expiry. Full Sprint 2 campaigns immediately await confirmation and cannot cancel. A legacy TargetReached campaign retains its pre-existing cancellation edge until operational cutover. Cancellation does not release campaign-wide committed stock: the campaign still offers its target. Acquisition expiry, rejection and confirmation timeout release the campaign's remaining commitment. Confirmed pickup windows also expire; uncollected reservations become Expired, pickups NotCollected, stock is released, and the group ends Failed. No code path treats these as financial refunds.

Inventory accounting uses variant units: AvailableQuantity is declared physical stock still on hand, CommittedQuantity is the sum of campaign holds, active reservation quantity is tracked separately, and FulfilledQuantity records physically verified collections. Free stock = available minus committed. Draft save checks free stock without holding it. Submission rechecks under the seller lock and commits the whole target; Admin rejection releases it. Collection reduces available and campaign commitment equally and increases fulfilled; historical fulfilled quantities are never added back to available. Commitments are conservative across all live campaigns, including disjoint schedules; there is no predicted replenishment. Stock declarations must cover existing holds and supply expectedVersion. Every collection invalidates stale inventory versions.

Campaign additions include decision key/actor/time/reason/outcome, confirmation/pickup deadlines, committed/fulfilled quantities and persisted worker retry metadata. Database checks bound nonnegative commitment/fulfillment, their sum to target, nonnegative inventory/version and pickup status/collection evidence. New scalar monetary/quantity fields retain the same numeric precision convention. Direct SQL remains an operator trust boundary for aggregate inventory conservation and cross-reservation pickup consistency; all HTTP writers use the transactional paths.

Sprint2Operations is schema-only. It preserves existing rows without inventing available stock, commitments or collection evidence. Existing active Sprint 1 rows with zero commitments are visible in Admin operations health and require reviewed cutover; new joins/approval/confirmation fail closed without inventory backing. Existing full/confirmed legacy rows without operational deadlines are not automatically timed out by the new worker. Resolve or explicitly migrate those commitments under an operator-reviewed plan before production upgrade; this sprint does not run such a data conversion. A fresh development seed declares synthetic stock for new demo campaigns.

Indexes cover public status/ID browsing, category sort, seller/campaign lookup, campaign expiry scans, customer reservation history, campaign reservation status, and audit timestamps. Application validation bounds strings and JSON; direct database access is restricted to trusted operators. There is no generic schema editing endpoint.
